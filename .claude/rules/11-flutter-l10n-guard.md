## What This Rule Does

Covers the **cost** side of localisation: the ARB pipeline, the generated
`AppLocalizations`, the language switcher, and bidirectional testing.

**Install condition:** only when `techContext.md` records `locales: multi`.
`/platform-init` installs it. An English-only project never sees this file.

The **free** side — using `start`/`end` instead of `left`/`right` — is
`07-flutter-direction-guard`, which is always on regardless of this rule.

## Non-Negotiables

### 1. No user-facing string literal in a widget

Every string a user can read comes from `AppLocalizations`. This includes
button labels, error messages, hint text, semantics labels, tooltips, dialog
titles, and empty-state copy.

Exempt: debug output, log lines, `Key` values, asset paths, and anything
tagged `// DEBUG-TEMP:`.

### 2. ARB is the source; generated code is not edited

`lib/l10n/app_en.arb` is authored. `AppLocalizations` is generated by
`flutter gen-l10n` and never hand-edited. If generated output is wrong, the
ARB or `l10n.yaml` is wrong.

Every key carries an `@key` description entry. A translator sees the key and
the description, never the surrounding code.

### 3. Plurals and genders use ICU, not `if`

```json
"orderCount": "{count, plural, =0{No orders} =1{1 order} other{{count} orders}}"
```

Never `count == 1 ? 'order' : 'orders'`. Arabic has six plural forms, Polish
has four, and the ternary is wrong in both before it is wrong anywhere else.

### 4. Dates, numbers and currency go through `intl`

`DateFormat.yMMMd(locale)`, `NumberFormat.currency(locale: ...)`. Never
`'${date.day}/${date.month}'` — that is `MM/DD` for one reader and `DD/MM` for
another, silently.

### 5. Every locale is complete before release

A missing key falls back to the template locale, which shows English inside an
Arabic screen. `/production-readiness-review` treats missing keys as `NO-GO`.

### 6. Golden tests run in every locale direction

For any screen with a golden test, at minimum one LTR and one RTL golden:

```dart
for (final locale in [const Locale('en'), const Locale('ar')]) {
  testWidgets('OrderCard golden ${locale.languageCode}', (tester) async {
    await tester.pumpWidget(MaterialApp(
      locale: locale,
      localizationsDelegates: AppLocalizations.localizationsDelegates,
      supportedLocales: AppLocalizations.supportedLocales,
      home: OrderCard(order: fakeOrder),
    ));
    await expectLater(
      find.byType(OrderCard),
      matchesGoldenFile('goldens/order_card_${locale.languageCode}.png'),
    );
  });
}
```

RTL goldens catch what LTR review cannot: overflow from longer translations,
mirrored icons that should not have mirrored, and physical padding that
`07-flutter-direction-guard` missed.

### 7. Fonts must cover the script

Arabic, Hebrew, Thai and CJK are not covered by every font. A missing glyph
renders as a box, and no test catches it — only a golden or a human does.
Confirm the font family declared in the theme supports every locked locale.

### 8. Locale is state, not a global

The selected locale is held by the app's state layer under
`02-flutter-state-guard`, persisted, and read by `MaterialApp`. Never a
top-level mutable variable.

## When Adding A New Locale

1. Copy the template ARB, translate values, keep keys identical
2. Add the `Locale` to `supportedLocales`
3. Add goldens for that locale on screens that already have goldens
4. Verify the theme font covers the script
5. Run `flutter gen-l10n` and commit the ARB — not the generated output, if
   generation runs in CI

## Relationship to Other Rules

- `07-flutter-direction-guard` — always on; this rule assumes it is satisfied
- `04-flutter-test-guard` — golden conventions
- `01-flutter-architecture-guard` — `AppLocalizations` is presentation-layer;
  domain and data never import it. A `Failure` carries a code, and the widget
  maps that code to a translated message.
