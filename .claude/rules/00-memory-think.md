## What This Rule Does

Before generating code, writing specs, running any skill, or answering any
non-trivial question, the agent reads the memory-bank to understand what
Flutter app it is in, what patterns are established, and what is currently
being worked on. This prevents the agent from making assumptions that
contradict the project's conventions — e.g. generating a `StateProvider` in
a repo that has already standardised on `AsyncNotifier`, or scaffolding a
new repository class when one for that resource already exists.

**Memory-bank is two-tiered** — see `memory-bank/README.md` for the full
breakdown. Tier 1 (`techContext.md`, `progress.md`, `activeContext.md`) is a
live snapshot regenerated by `/context-sync` and kept current by this rule.
Tier 2 (`architecture.md`, `domainRules.md`, `securityStandards.md`) is
human-authored standards content — never auto-regenerated, only read.

## Step 1 — Detect Project State

Read the following files **in order**, stopping once sufficient context is
established:

1. `memory-bank/techContext.md` → **the locked stack**: which state
   management this project uses (Cubit / Bloc / Riverpod), the error-handling
   shape that follows from it, DI, routing, SDK version. The line
   `Locked by: /platform-init` is what proves the decision was actually made
   rather than inferred.
2. `memory-bank/architecture.md` → established folder structure (feature-first
   vs layered), how features are organized.
3. `memory-bank/activeContext.md` → what is currently being worked on.
4. `memory-bank/progress.md` → what tasks are Done, In Progress, or Blocked —
   never re-implement something already done.

**If `techContext.md` is missing, is still a template, or lacks the
`Locked by: /platform-init` line**, the project's state-management style is
undecided. Stop before generating anything and output:

> **`/platform-init` has not run.** This project has no locked state-management
> style, so any generated code would be a guess. Run `/platform-init` first —
> it asks one question.

**If `memory-bank/` does not exist at all**, auto-detect from the file system
to inform that conversation — never to substitute for it:
- `pubspec.yaml` present → confirm this is a Flutter/Dart project
- `flutter_bloc` → Cubit or Bloc (grep `extends Bloc<` to tell which)
- `flutter_riverpod` / `hooks_riverpod` → Riverpod; `riverpod_generator` +
  `build_runner` means `@riverpod` annotation style
- **Both present** → stop and report it; that is a real defect in the repo
- `go_router`, `dio`, `get_it`, `freezed` → the rest of the stack
- Then output: **"No memory-bank found. Run `/platform-init`, then
  `/repo-discovery` and `/context-sync` to initialize it from the existing
  codebase before continuing."**

## Step 2 — Skill Auto-Routing (announce before running)

Before responding, check if the request matches a skill. The full catalog is
`WORKFLOW.md` at the repo root — read it at this step rather than relying on
memory of it.

| User intent | Skill | Then |
|---|---|---|
| Brand-new project, stack not yet decided | `platform-init` | announce, wait |
| Empty project needing its structure | `flutter-project-init` | announce, wait |
| No networking layer yet | `flutter-network-gen` | announce, wait |
| New widget | `flutter-widget-gen` | announce, wait |
| New screen + state + route | `flutter-screen-gen` | announce, wait |
| New Cubit / Bloc / Notifier | `flutter-state-gen` | announce, wait |
| New data-layer repository/data source | `flutter-repository-gen` | announce, wait |
| New freezed/json_serializable model | `flutter-model-gen` | announce, wait |
| Work too big for one sitting | `work-breakdown` | announce, wait |
| "How does this screen work today?" | `feature-trace` | announce, proceed |
| "What breaks if I change this?" | `impact-analysis` | announce, proceed |
| "Is the architecture/state clean" | `flutter-architecture-audit` / `flutter-performance-audit` | announce, proceed |
| "Is this ready to ship?" | `production-readiness-review` | announce, proceed |
| Start of a new session in an unmapped repo | `repo-discovery` | silent |
| `memory-bank/` missing or stale | `context-sync` | silent |

Every match gets announced in this exact shape before running:

> **Matched skill:** `skill-name` — [one-line description].

Generators wait for a go-ahead after announcing. Auditors/analysis proceed
automatically after announcing. Housekeeping (`repo-discovery`,
`context-sync`) runs silently.

## Step 3 — Post-Task Memory Update

After completing any significant task (code generation, plan finalization):

1. Update `memory-bank/activeContext.md` with what was just done, which
   files changed, and the next logical step.
2. Update `memory-bank/progress.md` if a task moved between Not Started /
   In Progress / Done, or a new blocker was discovered.

## Violations

### ❌ Violation 1 — Generating code without reading memory-bank

**Trigger:** User asks: *"Add a favorites list screen."*

**Bad behavior:**
> Agent immediately scaffolds a `StatefulWidget` with `setState`-managed list
> state — the project locked in Cubit two features ago and every other screen
> uses a sealed state class.

**Correct behavior:**
> Agent reads `memory-bank/techContext.md`, sees `State management: Cubit`
> and `Locked by: /platform-init`, reads `memory-bank/architecture.md` for the
> feature-first layout, and delegates to `pattern-scout` to find the nearest
> existing Cubit. Generates a `FavoritesCubit` + sealed `FavoritesState` in
> `features/favorites/presentation/cubit/`, matching the existing pattern.

### ❌ Violation 2 — Generating before the stack is locked

**Trigger:** User asks: *"Add a login screen"* in a fresh repo.

**Bad behavior:**
> Agent picks a state-management style on its own — usually whichever it saw
> most recently — and generates against it. Two weeks later half the app is
> Cubit and half is Riverpod.

**Correct behavior:**
> Agent checks `techContext.md`, finds no `Locked by: /platform-init` line,
> and stops: *"This project has no locked state-management style yet. Run
> `/platform-init` — one question — and I'll generate against the answer."*

### ❌ Violation 3 — Starting a feature already In Progress

**Trigger:** User asks: *"Start implementing the checkout flow."*

**Bad behavior:**
> Agent jumps straight to scaffolding without checking `progress.md` —
> creates a second `checkout/` feature folder when one already exists with
> three screens done.

**Correct behavior:**
> Agent reads `memory-bank/progress.md`, finds the checkout feature already
> In Progress with the cart and shipping screens Done. Responds with what's
> left (payment screen) instead of duplicating existing work.
